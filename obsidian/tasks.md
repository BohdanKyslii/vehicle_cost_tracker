## Зроблено (2026-09-17)

- **`import_file` підтверджено робочим + реальний ESP/OPT імпорт на
  прод.** Спростовано власну нотатку від 2026-09-10 ("ендпоінта нема")
  — вона сама була хибною. Живо імпортовано два реальні тижневі
  реєстри (`Переміщення з БЦ на АЗС реєстр 2026 - ESP.xls`/`..._OPT.xls`)
  через `/waybills/import`: 2613 рядків ЄСП + 77 ОПТ, 0 помилок.
  Файли довелось попередньо переформатувати (заголовок "№" замість
  пробілу, "АЗС" кирилицею замість "AZS", службовий рядок над
  заголовком) — деталі й чому саме так у [[esp-opt-xls-reformat-for-import]].
- **Виправлено реєстр `/waybills`** ("Не вдалось завантажити
  накладні"): `src/api/waybills.ts` бив у неіснуючий `/api/waybills/`
  замість `/api/waybill-records/`, і — окремо — не мапив сиру
  DRF-відповідь бекенду (snake_case, по товарних рядках) у форму, яку
  чекає UI (camelCase, агрегація по накладній). Додано
  `RawWaybillLine`/`mapLineToSummary`. Два коміти, задеплоєно, живо
  перевірено в браузері (список показує реальні 4518 рядків). **Без
  справжньої агрегації по `waybill_number`** — користувач свідомо
  обрав швидкий фікс шляху замість повної агрегації, коли спитали;
  кожен товарний рядок зараз = окремий рядок таблиці
  (`linesCount` завжди 1). Деталі відкритого — [[waybills-list-real-api-gap]].

## Наступний крок

1. **Справжня агрегація реєстру накладних по `waybill_number`** —
   зараз `/waybills` показує рядок на кожну товарну позицію, а не на
   накладну (див. вище). Потребує рішення: агрегувати на фронтенді
   (ламає серверну пагінацію — довелось би пагінувати по унікальних
   накладних, не по рядках) чи додати окремий агрегуючий ендпоінт на
   бекенді. Не зроблено — відкладено користувачем 2026-09-17.
   Також окремо биті `WaybillDetail`/channel-check (лукап по `pk`, не
   по номеру накладної) — те саме джерело, [[waybills-list-real-api-gap]].
2. **134 підозрілих тестових товари в проді** — знайдено одноразовим
   аудитом (видалений після), не видалені (не було явного дозволу
   користувача). Деталі — [[open-items-2026-09-10]].
3. **`CATEGORY_DEFAULTS.CHILD_OTHER` (id 15) застарілий** — тепер
   реальна категорія "Los Monteros" (вино), не generic "Інше"; фолбек
   при створенні товару без категорії мовчки мис-категоризує. Не
   виправлено, поза межами того, що просив користувач.
4. `WaybillDetail`, `/waybills/unassigned`, `/waybills/returns`
   лишаються не набраними.
5. Аналітика/графіки (Recharts) — і бекенд (`apps.analytics`), і
   фронтенд свідомо не почато.
6. Перевірити backend-репо `vehicle_tracker_api` — попередні нотатки
   (2026-08-30) стверджували, що `apps.logistics` серіалізатори/views
   для Фаз 18-19 закомічені локально, але НЕ запушені; звірку не
   повторювали. Якщо щось із цього досі не запушено — прод може
   працювати проти старішого бекенду, ніж очікується.
7. Дрібне: `findEventGroup()` тепер групує за явним маркером
   `[stop:N]` у `notes`, НЕ за часовою евристикою (замінено ще
   2026-08-28, той самий день, що й Фаза 17 — старі записи без
   маркера залишаються кожен сам собі групою).

## Відкриті питання

- `package-lock.json` — досі дрібні локальні розходження, не мої,
  не займав жодного разу.
- Інший процес комітить/мержить у `main` незалежно від цієї сесії —
  перед плануванням нової гілки звіряй `git log`.
- Panel-management, waybill inline-edit і весь довідниковий блок
  2026-09-10 (Категорії/видалення/фільтри/пагінація) не описані як
  окремі Кроки/Фази `CODING_GUIDE.md` — зафіксовано підсумковим
  датованим блоком у "## Наступні кроки" (2026-09-10), а не дописано
  заднім числом як повноцінний Крок, за аналогією з попередніми
  недокументованими шматками.
