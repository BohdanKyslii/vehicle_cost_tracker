# vehicle_cost_tracker — архітектурні рішення

## Навчальний формат проєкту

Весь код пишеться крок за кроком за `CODING_GUIDE.md` — покроковою
інструкцією для вивчення JS/React/TS з нуля. Кожна фаза = окремий розділ
гайду з поясненнями "навіщо", а не тільки "що робити". Це впливає на темп:
код навмисно пишеться повільніше й послідовніше, ніж міг би.

## Розділення на два репозиторії

Один застосунок (облік транспортних витрат) розділено на:
- `vehicle_cost_tracker` (цей репо) — React PWA фронтенд.
- `vehicle_tracker_api` — Django-бекенд (`C:\Users\b.kysliy\PycharmProjects\vehicle_tracker_api\`).

Причина розділення в контексті не зафіксована окремо — прийнято як
стандартний підхід frontend/backend-репо.

## CSS: Tailwind + окремий CSS-файл для лендінгу

Проєкт має Tailwind у залежностях, але лендінг (`TopNav`, `LandingPage`,
`AuthModal`) написаний на чистому CSS (`src/styles/landing.css`), не
Tailwind-класами. Рішення явно проговорене в `CODING_GUIDE.md` (Крок 3.4)
як усвідомлений вибір для цієї частини — Tailwind лишається для основної
частини застосунку (форми, таблиці, дашборди).

## Auth: cookie, не localStorage

Фаза 4.5 гайду явно обирає cookie-based авторизацію замість localStorage
(Крок 4.5.1 — "Чому cookie, а не localStorage"). Мотивація в гайді:
безпека (XSS не може вкрасти httpOnly cookie) — типове для Django-сесій
рішення, узгоджене з бекендом на `vehicle_tracker_api`.

## `.env`: mock-дані до готовності бекенда

`VITE_USE_MOCK` дозволяє розробляти фронтенд на JSON mock-даних, поки
Django backend (`vehicle_tracker_api`) не готовий або недоступний
локально. `VITE_API_BASE` перемикається між localhost (dev) і
продакшн-доменом (`.env.production`).

## Деплой: власний Raspberry Pi замість хмарного хостингу

Продакшн — домен `warehouse.mom`, що резолвиться на Raspberry Pi вдома,
доступ через Cloudflare Tunnel (`cloudflared`), не прямий порт-форвардинг.
Автодеплой через GitHub Actions: push у `main` → SSH на Pi через тунель →
`git pull` + `docker compose build/up`. Рішення дає повний контроль і
нульову вартість хостингу ціною ручного адміністрування заліза.

## Git-флоу: гілка на фазу, `main` = продакшн

Починаючи з Фази 5 (після налаштування автодеплою у Фазі 4), кожна фаза
розробляється в окремій гілці з PR у `main`, а не напряму. Причина явно
зафіксована в гайді: `main` автоматично деплоїться на `warehouse.mom`,
тому незавершений/зламаний код туди потрапляти не повинен. Фази 1-4
писались напряму в `main`, поки коду було мало і автодеплою ще не було.

## `src/hocks/` — тайпо в назві теки залишено свідомо

Тека хуків названа `hocks` (без другого "o") ще з Фази 3
(`useAuthModal.ts`) — виправлення на `hooks` зараз означало б переписати
всі існуючі імпорти. `CODING_GUIDE.md` (Кроки 4.5.4-4.5.7) у прикладах
коду пише правильне `../../hooks/useCurrentUser` — це розбіжність
гайду з реальною структурою репо, не помилка в коді. При реалізації
нового кроку з гайду копіювати шлях імпорту напряму з тексту гайду
не можна — треба підставляти `hocks`. Саме ця розбіжність спричинила
"файл підкреслений червоним" у `TopNav.tsx` (Крок 4.5.7): імпорт
скопіювали з гайду як `hooks`, а такої теки не існує.

## DriverLayout і MainLayout лишаються окремими дизайн-системами (2026-08-11)

Водій відкриває застосунок як Telegram Mini App (WebView, мобільний
екран, bottom nav) — офіс/логіст працює з десктопного браузера
(sidebar, ширші таблиці). Замість об'єднання в одну навігацію
(наприклад, показувати `TopNav` і на driver-сторінках) вирішено
лишити `DriverLayout`/`MainLayout` окремими, а замість цього
виправити СПРАВЖНЮ проблему — відсутність спільної точки входу:
`/` мав вести на `LandingPage` (`CODING_GUIDE.md`, Крок 13.6), а
реально веде жорстким `Navigate` на `/driver` для всіх, і `LandingPage`/
`TopNav`/`AuthModal` зараз ніде не рендеряться. `CODING_GUIDE.md` Фаза 14
(`RequireRole`/`RoleRedirect`) вирішує саме це: `/` → `LandingPage` для
неавторизованих, після логіну — редирект у СВІЙ layout за роллю
(`driver` → `/driver`, решта → `/fleet`), а не одну спільну навігацію
для всіх ролей. Причина рішення "не мерджити" — різна аудиторія й
контекст використання (мобільний Telegram WebView водія vs десктопний
офісний застосунок логіста), а не технічне обмеження.

## Логіст (`role=logist`) отримує права на запис в автопарк, не лише manager/head (2026-08-11)

`apps/accounts/permissions.py::IsManagerOrHead` (бекенд) спершу мав
`allowed_roles = ('manager', 'head')` — без `logist`. Задача явно
вимагає, щоб саме логіст міг додавати авто через сайт, тому
`DJANGO_CODING_GUIDE.md` Фаза 9.2 вводить окремий `IsLogistOrAbove`
(`logist`/`manager`/`head`) для запису в `/api/cars/`, `/api/drivers/`
— `IsManagerOrHead` лишається окремо для того, де саме логіст НЕ
повинен мати доступу (наприклад, майбутнє підтвердження реєстрацій
користувачів, "Крок 15" у "Що далі").

## Сканування накладної не потребує нової моделі на бекенді (2026-08-11)

Спокуса була завести окрему сутність "скановане фото/QR накладної".
Але `RouteEvent` (бекенд, Фаза 3.7) вже має `waybill_number`/
`waybill_date`/`customer_name` саме для типу події `delivery` — робочий
`EventForm` уже відправляє ці поля через `POST /api/route-events/`.
Рішення: сканер (`CODING_GUIDE.md` Фаза 15, `html5-qrcode` +
`src/utils/parseQR.ts`, уже готовий парсер) лише підставляє готові
значення в ті самі поля замість ручного набору — жодних змін моделі
чи нового endpoint'у на бекенді не треба (`DJANGO_CODING_GUIDE.md`,
Крок 10.4).

## `DriverHistory` показує лише СЬОГОДНІШНІ події, не всю історію (2026-08-28)

Фаза 17 спершу прибрала список "Події сьогодні" з `DriverDashboard`,
розраховуючи, що водій побачить ті самі події в `DriverHistory` (яка
тягне `useDriverEvents` — усю історію, найновіші зверху). На практиці
це виявилось неправильним UX: якщо за сьогодні ще нічого не
відскановано, водій бачить учорашні події й не розуміє, що це не
сьогоднішні. Рішення — `DriverHistory`/`EventDetail` тепер тягнуть
`useTodayEvents` (сервер сам рахує "сьогодні" через `date=today`),
а не всю історію. `useDriverEvents`/`fetchDriverEvents` лишились у
коді (не видалені) — можуть знадобитись для майбутньої окремої
сторінки "повна історія", якщо вона колись знадобиться, але зараз
жодна сторінка їх не використовує.

## Групування накладних однієї точки — явний маркер у `notes`, не часова евристика (2026-08-28, переглянуто того ж дня)

`RouteEvent` не має поля-групи (свідомий вибір ще Фази 15 — див. розділ
вище "Сканування накладної не потребує нової моделі на бекенді"). Перша
версія `findEventGroup()` (`eventHelpers.ts`) вираховувала групу
часовою евристикою: усі `delivery`-події того ж `trackingMode` без
розриву довше 10 хвилин — однією точкою. Живе тестування одразу
показало, що це неправильно: водій сканував кілька ОКРЕМИХ,
самостійних накладних "по одній" (кожну — окремим заходом в
`EventForm`, без "+ Ще одна накладна"), і вони випадково потрапляли у
вікно 10 хв — евристика хибно об'єднувала їх в одну "точку", хоча
жодного реального зв'язку не було.

Замінено на явний маркер: додаткова накладна (створена через
"+ Ще одна накладна" в `EventForm` чи "Ще одна накладна цієї точки" в
`EventDetail`) отримує в `notes` префікс `[stop:<id основної події>]`;
`findEventGroup()` групує за цим маркером (чи власним `id`, якщо
маркера нема), а не за близькістю в часі. Самостійна подія БЕЗ маркера
завжди сама собі група, незалежно від того, наскільки близько вона за
часом до інших. `eventComment()` прибирає маркер перед показом водієві
(`stripStopTag()`).

Компроміс: старі записи (створені до цього фікса), згруповані виключно
за часовою евристикою, після деплою розпадуться на окремі — у них
немає маркера `[stop:N]`, а backfill не робили. Прийнято свідомо: фіча
нова, реальних продакшн-груп на момент фікса було мало, хибне
групування шкідливіше за втрату старого групування заднім числом.

## Підтвердження видалення — "два дотики", не `window.confirm()` (2026-08-28)

Видалення події/накладної (`EventDetail.tsx`, Фаза 17) підтверджується
повторним натисканням тієї самої кнопки (перший клік → 3 секунди кнопка
показує "Точно?", другий клік у цьому вікні виконує видалення), а не
нативний `confirm()`. Причина: нативний діалог блокує весь інтерфейс і
виглядає чужорідно на мобільному екрані; двократний дотик — звичний
мобільний патерн (як "смахнути, щоб видалити" в багатьох застосунках),
не вимагає окремого компонента-модалки.

## `useMutation.onSuccess` з інвалідацією кешу МАЄ повертати проміс (2026-08-28)

Знайдено на живому тестуванні Фази 17: `useCreateRouteEvent`
(`useRouteEvents.ts`, Фаза 7) інвалідував кеш у `onSuccess` без
`return` — `mutateAsync()` резолвився одразу після POST, не чекаючи
реального оновлення `todayEvents`. Це давало вікно гонки: дублікат-гард
у `EventForm.tsx` (Фаза 15) перевіряє нову накладну проти
`todayEvents`, і якщо водій відкривав наступний скан ДО завершення
фонового refetch, гард ще бачив старі дані — повторне сканування тієї
самої накладної інколи проходило, хоча мало блокуватись. Правило на
майбутнє: якщо код після `await mutation.mutateAsync(...)` покладається
на СВІЖІ дані з інвалідованого запиту (а не просто на побічний ефект
"десь колись оновиться") — `onSuccess`/`onSettled` цієї мутації
ОБОВ'ЯЗКОВО має `return Promise.all([...invalidateQueries...])`, інакше
`mutateAsync` не чекає на реальний refetch.
