# vehicle_cost_tracker — архітектурні рішення

## Навчальний формат проєкту

Весь код пишеться крок за кроком за `CODING_GUIDE.md` — покроковою
інструкцією для вивчення JS/React/TS з нуля. Кожна фаза = окремий розділ
гайду з поясненнями "навіщо", а не тільки "що робити". Це впливає на темп:
код навмисно пишеться повільніше й послідовніше, ніж міг би.

## Розділення на два репозиторії

Один застосунок (облік транспортних витрат) розділено на:
- `vehicle_cost_tracker` (цей репо) — React PWA фронтенд.
- `vehicle_tracker_api` — Django-бекенд (`C:\Users\b.kysliy\PycharmProjects\vehicle_tracker_api\`).

Причина розділення в контексті не зафіксована окремо — прийнято як
стандартний підхід frontend/backend-репо.

## CSS: Tailwind + окремий CSS-файл для лендінгу

Проєкт має Tailwind у залежностях, але лендінг (`TopNav`, `LandingPage`,
`AuthModal`) написаний на чистому CSS (`src/styles/landing.css`), не
Tailwind-класами. Рішення явно проговорене в `CODING_GUIDE.md` (Крок 3.4)
як усвідомлений вибір для цієї частини — Tailwind лишається для основної
частини застосунку (форми, таблиці, дашборди).

## Auth: cookie, не localStorage

Фаза 4.5 гайду явно обирає cookie-based авторизацію замість localStorage
(Крок 4.5.1 — "Чому cookie, а не localStorage"). Мотивація в гайді:
безпека (XSS не може вкрасти httpOnly cookie) — типове для Django-сесій
рішення, узгоджене з бекендом на `vehicle_tracker_api`.

## `.env`: mock-дані до готовності бекенда

`VITE_USE_MOCK` дозволяє розробляти фронтенд на JSON mock-даних, поки
Django backend (`vehicle_tracker_api`) не готовий або недоступний
локально. `VITE_API_BASE` перемикається між localhost (dev) і
продакшн-доменом (`.env.production`).

## Деплой: власний Raspberry Pi замість хмарного хостингу

Продакшн — домен `warehouse.mom`, що резолвиться на Raspberry Pi вдома,
доступ через Cloudflare Tunnel (`cloudflared`), не прямий порт-форвардинг.
Автодеплой через GitHub Actions: push у `main` → SSH на Pi через тунель →
`git pull` + `docker compose build/up`. Рішення дає повний контроль і
нульову вартість хостингу ціною ручного адміністрування заліза.

## Git-флоу: гілка на фазу, `main` = продакшн

Починаючи з Фази 5 (після налаштування автодеплою у Фазі 4), кожна фаза
розробляється в окремій гілці з PR у `main`, а не напряму. Причина явно
зафіксована в гайді: `main` автоматично деплоїться на `warehouse.mom`,
тому незавершений/зламаний код туди потрапляти не повинен. Фази 1-4
писались напряму в `main`, поки коду було мало і автодеплою ще не було.

## `src/hocks/` — тайпо в назві теки залишено свідомо

Тека хуків названа `hocks` (без другого "o") ще з Фази 3
(`useAuthModal.ts`) — виправлення на `hooks` зараз означало б переписати
всі існуючі імпорти. `CODING_GUIDE.md` (Кроки 4.5.4-4.5.7) у прикладах
коду пише правильне `../../hooks/useCurrentUser` — це розбіжність
гайду з реальною структурою репо, не помилка в коді. При реалізації
нового кроку з гайду копіювати шлях імпорту напряму з тексту гайду
не можна — треба підставляти `hocks`. Саме ця розбіжність спричинила
"файл підкреслений червоним" у `TopNav.tsx` (Крок 4.5.7): імпорт
скопіювали з гайду як `hooks`, а такої теки не існує.

## DriverLayout і MainLayout лишаються окремими дизайн-системами (2026-08-11)

Водій відкриває застосунок як Telegram Mini App (WebView, мобільний
екран, bottom nav) — офіс/логіст працює з десктопного браузера
(sidebar, ширші таблиці). Замість об'єднання в одну навігацію
(наприклад, показувати `TopNav` і на driver-сторінках) вирішено
лишити `DriverLayout`/`MainLayout` окремими, а замість цього
виправити СПРАВЖНЮ проблему — відсутність спільної точки входу:
`/` мав вести на `LandingPage` (`CODING_GUIDE.md`, Крок 13.6), а
реально веде жорстким `Navigate` на `/driver` для всіх, і `LandingPage`/
`TopNav`/`AuthModal` зараз ніде не рендеряться. `CODING_GUIDE.md` Фаза 14
(`RequireRole`/`RoleRedirect`) вирішує саме це: `/` → `LandingPage` для
неавторизованих, після логіну — редирект у СВІЙ layout за роллю
(`driver` → `/driver`, решта → `/fleet`), а не одну спільну навігацію
для всіх ролей. Причина рішення "не мерджити" — різна аудиторія й
контекст використання (мобільний Telegram WebView водія vs десктопний
офісний застосунок логіста), а не технічне обмеження.

## `DriverHistory` показує лише СЬОГОДНІШНІ події, не всю історію (2026-08-28)

Фаза 17 спершу прибрала список "Події сьогодні" з `DriverDashboard`,

сторінки "повна історія", якщо вона колись знадобиться, але зараз
жодна сторінка їх не використовує.

## Групування накладних однієї точки — явний маркер у `notes`, не часова евристика (2026-08-28, переглянуто того ж дня)

`RouteEvent` не має поля-групи (свідомий вибір ще Фази 15 — див. розділ
вище "Сканування накладної не потребує нової моделі на бекенді"). Перша
версія `findEventGroup()` (`eventHelpers.ts`) вираховувала групу
часовою евристикою: усі `delivery`-події того ж `trackingMode` без
розриву довше 10 хвилин — однією точкою. Живе тестування одразу
показало, що це неправильно: водій сканував кілька ОКРЕМИХ,
самостійних накладних "по одній" (кожну — окремим заходом в
`EventForm`, без "+ Ще одна накладна"), і вони випадково потрапляли у
вікно 10 хв — евристика хибно об'єднувала їх в одну "точку", хоча
жодного реального зв'язку не було.

Замінено на явний маркер: додаткова накладна (створена через
"+ Ще одна накладна" в `EventForm` чи "Ще одна накладна цієї точки" в
`EventDetail`) отримує в `notes` префікс `[stop:<id основної події>]`;
`findEventGroup()` групує за цим маркером (чи власним `id`, якщо
маркера нема), а не за близькістю в часі. Самостійна подія БЕЗ маркера
завжди сама собі група, незалежно від того, наскільки близько вона за
часом до інших. `eventComment()` прибирає маркер перед показом водієві
(`stripStopTag()`).

Компроміс: старі записи (створені до цього фікса), згруповані виключно
за часовою евристикою, після деплою розпадуться на окремі — у них
немає маркера `[stop:N]`, а backfill не робили. Прийнято свідомо: фіча
нова, реальних продакшн-груп на момент фікса було мало, хибне
групування шкідливіше за втрату старого групування заднім числом.

## Підтвердження видалення — "два дотики", не `window.confirm()` (2026-08-28, ЗАМІНЕНО 2026-08-31)

Видалення події/накладної (`EventDetail.tsx`, Фаза 17) спершу
підтверджувалось повторним натисканням тієї самої кнопки (перший клік →
3 секунди кнопка показує "Точно?", другий клік у цьому вікні виконує
видалення), а не нативний `confirm()`. Причина: нативний діалог блокує
весь інтерфейс і виглядає чужорідно на мобільному екрані.

**2026-08-31 — замінено на явну картку-підтвердження** (компонент
`ConfirmDeleteMessage` у `EventDetail.tsx`): текст "Видалити накладну
№X?"/"Видалити цю подію?" + дві окремі кнопки "Так, видалити"/
"Скасувати". Причина заміни: "той самий текст на кнопці міняється" не
читався як окремий крок підтвердження — легко натиснути другий раз
не помітивши, що це вже видалення, а не звичайний клік. Явна картка з
двома різними кнопками усуває цю двозначність ціною одного зайвого
елемента в DOM замість переиспользования тієї самої кнопки.

## Виправлення помилково відсканованої накладної без пересканування (2026-08-31)

До цього єдиним способом виправити помилку в уже збереженій накладній
(неправильний номер/дата/клієнт через збій сканера чи людську помилку)
було видалити подію й сканувати нову — незручно, якщо помилка дрібна
(одна цифра в номері). Додано `PATCH /route-events/:id/`
(`updateRouteEvent()` у `src/api/routeEvents.ts`, тип `RouteEventPatch`)
— саме PATCH, не PUT, щоб можна було міняти підмножину полів
(номер/дата/клієнт/одометр/палети), не займаючи решту події (тип, час,
авто/водій, зв'язок `[stop:N]`). Інлайн-форма редагування прямо в
списку накладних `EventDetail.tsx`, без окремої сторінки/модалки.

## `useMutation.onSuccess` з інвалідацією кешу МАЄ повертати проміс (2026-08-28)

Знайдено на живому тестуванні Фази 17: `useCreateRouteEvent`
(`useRouteEvents.ts`, Фаза 7) інвалідував кеш у `onSuccess` без
`return` — `mutateAsync()` резолвився одразу після POST, не чекаючи
реального оновлення `todayEvents`. Це давало вікно гонки: дублікат-гард
у `EventForm.tsx` (Фаза 15) перевіряє нову накладну проти
`todayEvents`, і якщо водій відкривав наступний скан ДО завершення
фонового refetch, гард ще бачив старі дані — повторне сканування тієї
самої накладної інколи проходило, хоча мало блокуватись. Правило на
майбутнє: якщо код після `await mutation.mutateAsync(...)` покладається
на СВІЖІ дані з інвалідованого запиту (а не просто на побічний ефект
"десь колись оновиться") — `onSuccess`/`onSettled` цієї мутації
ОБОВ'ЯЗКОВО має `return Promise.all([...invalidateQueries...])`, інакше
`mutateAsync` не чекає на реальний refetch.

## Локед-режим форм і кастомне підтвердження видалення — тепер явне правило проєкту, не лише де вже було (2026-08-31, живе тестування `/panel/events`)

Живе тестування `EventAdminForm.tsx` одразу виявило, що новий адмінський
редактор події не мав ані локед-режиму (`isEditingDetails`/`detailsLocked`,
уже усталений в `CarForm.tsx`/`ProductForm.tsx`/...), ані можливості
додати ще одну накладну до вже створеної точки (те, що driver'у доступно
через `EventDetail.tsx`). Виправлено: `EventAdminForm.tsx` тепер за
замовчуванням locked при редагуванні (весь набір полів, не лише
підмножина, як у `CarForm`, — у події немає "завжди доступних" селектів
на кшталт статусу авто); секція "Накладні цієї точки" (список +
"+ Ще одна накладна цієї точки", той самий маркер `[stop:N]`) доступна
під час розблокованого редагування.

Заразом користувач явно зафіксував це як ЗАГАЛЬНЕ правило проєкту, не
разовий фікс однієї форми — збережено в пам'яті Claude Code
([[locked-edit-form-pattern-required]], [[destructive-action-confirmation-required]]):
(1) будь-яка форма редагування наявного запису має відкриватись
заблокованою, з "✏️ Редагувати" для розблокування, і кнопка
"назад"/"скасувати" ніколи не зберігає; (2) будь-яке видалення має
явне UI-підтвердження — новий спільний `src/components/ui/ConfirmDelete.tsx`
(світла/панельна версія `ConfirmDeleteMessage` з `driver/EventDetail.tsx`)
замінив `window.confirm()` у `EventsAdminList.tsx` і inline-видалення
накладних у `EventAdminForm.tsx`.

Побічно знайдено й виправлено реальний баг: порожнє поле "Дата
накладної" в `EventAdminForm.tsx` слало порожній рядок (не `null`) у
`waybill_date` — бекенд відповідав 400 "Невірний формат дати". Той
самий патерн (`needsWaybill && waybillDate ? waybillDate : undefined`,
не просто `needsWaybill ? waybillDate : undefined`) слід копіювати, а
не патерн з `driver/EventForm.tsx`, де ця гілка "випадково" безпечна
лише тому, що там дата завжди приходить зі сканера QR.

**Наступний раунд живого тестування того ж дня знайшов ще два баги в
цій самій фічі:**
1. `handleAddWaybill()` (додати ще одну накладну цієї точки) слав
   `eventTs: new Date().toISOString()` — "зараз", а не час ОСНОВНОЇ
   події. Для події заднім числом (не сьогоднішньої) додаткова
   накладна лягала під сьогоднішньою датою — випадала з фільтра
   "дата" адмінського списку/групи (обидва фільтрують за датою
   основної події) і виглядала як самостійна нова подія "нізвідки".
   Виправлено: `eventTs: existing.eventTs` (той самий час, що в
   основної події точки).
2. Фільтри `EventsAdminList.tsx` (дата/авто/водій) жили в
   `useState` — при переході на `/panel/events/:id` і назад компонент
   розмонтовувався й монтувався заново, фільтри скидались на
   "сьогодні"/"усі". Виправлено: фільтри тепер у `useSearchParams`
   (URL `?date=...&carId=...&driverId=...`), а всі `navigate("/panel/events")`
   в `EventAdminForm.tsx` (скасувати, після створення, після
   збереження) замінено на `navigate(-1)` — повертає САМЕ на той URL
   зі списку, з якого прийшли, фільтри не втрачаються. Компроміс:
   якщо на `/panel/events/new` чи `/panel/events/:id` потрапити напряму
   за URL (без переходу зі списку), `navigate(-1)` піде за межі SPA
   (у попередню сторінку браузера) — прийнятно, бо в цьому проєкті
   ніде більше немає підтримки прямих deep-link заходів у форми.

## `/admin` не використовується як SPA-маршрут — кастомна адмінка живе на `/panel` (2026-08-30)

nginx на проді проксіює `/admin/` напряму на Django admin (`nginx.conf`)
— клієнтський React-роут з такою назвою був би недосяжний, nginx
перехопить запит раніше, ніж він дійде до `index.html`. Тому кастомний
"суперкористувацький" розділ застосунку (довідники товарів/клієнтів/
магазинів, керування користувачами) свідомо названо `/panel`, не
`/admin`. Симптом до фіксу (Фаза 21, Крок 21.1): Service Worker
перехоплював навігацію на `/panel` і повертав 404, бо denylist був
написаний під стару назву `/admin` — виправлено додаванням `/panel` у
відповідний список, а не перейменуванням назад.

## Product/Customer/Store типи виправлено проти реального DRF-виводу, не проти `documents/` (2026-08-30)

`documents/01-08` (design-довідник, ресинхронізовано 2026-08-24 — див.
розділ вище) описував форму цих сутностей ДО того, як з'явився перший
реальний споживач у фронтенді. Коли `panel-management` почав реально
викликати `apps.products`/`apps.customers`, виявилось, що частина полів
у `types/index.ts` була придумана заздалегідь і не відповідала
серіалізаторам бекенду: `ProductCategory.idCategory` → `id`,
`parentID` → `parent` + додано `isRoot`/`parentName`; `Store.idCustomer`
→ `customer` (FK id) + `customerName`; `Customer` отримав
`storesCount`. Підтверджує загальний висновок попереднього рішення:
`documents/` — бізнес-контекст, не контракт API, доки поле не
перевірене напряму проти відповіді бекенду.

## `/panel/events`: адмінський CRUD подій водіїв не потребував БУДЬ-ЯКИХ змін бекенду (2026-08-31)

Задача — дати head можливість переглянути/поправити/додати подію
довільного водія на етапі живого тестування ([[driver-live-testing-loop]]).
Дослідження `RouteEventViewSet` (`apps/cars/views.py`, бекенд) показало:
`get_queryset()` фільтрує чергу лише для `profile.role == "driver"` —
`logist`/`manager`/`head` вже й так бачать і можуть редагувати/видаляти
ВСІ події без жодного додаткового фільтра; `perform_create()` форсує
`driver`/`car` з сесії теж лише для ролі `driver`, будь-яка інша роль
зберігає подію з довільними `car`/`driver` із тіла запиту.
`RouteEventCreateSerializer` (`exclude = ["id", "created_at"]`) не має
read-only полів — усі поля вже редаговані. Тобто фіча — суто фронтенд:
нова сторінка (`EventsAdminList`/`EventAdminForm`, `/panel`, head-only) і
розширення `RouteEventPatch` (`src/api/routeEvents.ts`) з 5 полів до
всіх полів `RouteEvent`, щоб один і той самий PATCH обслуговував і
вузьке водійське редагування (`EventDetail.tsx`), і повне адмінське.

## Масовий Excel-імпорт довідників: парсинг на фронтенді, без bulk-ендпоінту на бекенді (2026-08-31)

Товари/Клієнти/Магазини (`/panel`) потрібно було наповнювати масово, не
рядок за рядком через форму. Дослідження бекенду показало: жодного
bulk-create ендпоінту немає ніде в проєкті (грепнуто `bulk`/`import`/
`openpyxl`/`pandas` — нуль збігів), а PK-поля цих трьох моделей
(`id_product`/`id_customer`/`id_store` — з 1С, не auto-increment) уже
приймаються звичайним `POST` (не позначені `read_only` в серіалізаторах).
Замість нового бекенд-ендпоінту — фронтенд парсить `.xlsx` (бібліотека
`xlsx`/SheetJS) і виконує послідовний цикл `POST` по рядку, той самий
підхід, що вже є в `BulkMonthlyCostsForm.tsx` для місячних витрат
(послідовно, не `Promise.all` — простіше зібрати помилку саме по
конкретному рядку, і бекенд однаково не отримує вигоди від
паралельних POST на ту саму таблицю). Наслідок: Магазини вимагають, щоб
рядок з "ID клієнта" посилався на вже створеного Клієнта (`customer` —
обов'язковий FK, `on_delete=RESTRICT`) — імпортувати Клієнтів раніше
Магазинів, порядок задокументовано прямо в UI сторінки імпорту, а не
розв'язано автоматично (сортування/двопрохідний імпорт визнано зайвим
для обсягів довідників, які ведуться вручну в 1С).

## `xlsx` встановлено з CDN SheetJS, не з npm-реєстру (2026-08-31)

Остання опублікована в npm версія `xlsx` (0.18.5) має 2 відомі CVE
(prototype pollution, ReDoS) — SheetJS припинив публікувати виправлення
в npm-реєстр і випускає патчені білди лише через власний CDN. Спроба
`npm install https://cdn.sheetjs.com/...` була заблокована захисним
класифікатором Claude Code як нетипова команда (інсталяція не з
реєстру) — користувач явно підтвердив дозвіл через AskUserQuestion
перед виконанням. `package.json` тепер посилається на URL tarball
замість номера версії — це очікувано й нормально для цього пакета,
не помилка при майбутньому `npm install`/рев'ю залежностей.
