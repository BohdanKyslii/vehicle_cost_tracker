## 1. Бізнес-контекст

Компанія має автопарк вантажних авто (доставка напоїв/товарів).
Наразі облік витрат ведеться вручну в Excel — немає оперативних даних
про пробіги, витрати палива, транспортну собівартість по накладних.

**Цілі системи:**
- Автоматизувати щоденний збір даних від водіїв (пробіг, паливо, накладні).
- Розраховувати повну собівартість доставки по кожній накладній і товару.
- Охопити всі канали доставки: власний автопарк, найманий транспорт, служби доставки.
- Надати менеджменту аналітичні дашборди по авто, маршрутах, витратах.
- Підготувати дані для майбутньої інтеграції з 1С/BAS.

| Роль (код) | Назва | Пристрій | Основні дії |
|------|------|----------|-------------|
| `driver` | Водій | Смартфон, **Telegram Mini App** (не звичайний PWA-інсталл — див. розділ 9) | Щоденний пробіг, паливо, сканування QR накладних, повернення, додатковий вантаж |

## 3. Канали доставки

Кожна накладна належить **рівно одному** каналу. Канал визначається при скануванні
або внесенні вручну. Подвійне призначення виключено на рівні бізнес-логіки.

⏳ Реалізовано поки лише сканування/типи подій водія (власний автопарк, Фаза 13);
найманий транспорт і служби доставки — тільки в типах/схемі, без UI.

| Канал | Хто вносить | Модель витрат | Статус |
|-------|------------|---------------|--------|
| **Власний автопарк** | Водій (Mini App) | Місячні витрати на авто, розподілені по накладних | ✅ QR-сканування набране (Фаза 15) |
| **Найманий транспорт** | Логіст (ПК) | Фактична вартість рейсу, прив'язана до накладних | ⏳ не розпочато |
| **Служби доставки** | Менеджер (ПК) | Реєстри витрат від НП / Міст Експрес | ⏳ не розпочато |

## 4. Два режими трекінгу водія (власний автопарк)

✅ Реалізовано в `EventForm.tsx`/`eventHelpers.ts` (Фаза 13, уточнено
Фаза 15 і резинхронізовано 2026-08-27 після тестування з водієм —
детально нижче). Логіст задає **дефолтний режим** на рівні авто
(`cars.default_tracking_mode`). Водій може **змінити режим на поточний
день** самостійно (`DayModeSwitch`, `useDayMode` — зберігається в
`localStorage`, ключ `dayMode:{дата}`, скидається щодня до дефолту авто).

> **Ключове розмежування (звідки й назва тайла різна):** тип `delivery`
> технічно один і той самий у БД в обох режимах, але означає РІЗНЕ:
> - `daily` → просто "Скан накладної" — реєстрація того, що накладна
>   сьогодні в маршруті; без одометра/палет (вони вже зафіксовані
>   разово в `depot_start`)
> - `full` → повноцінне "Вивантаження" на конкретній точці — одометр +
>   палети саме тут потрібні, бо з них рахується пробіг/час між точками

### Режим `daily` — щоденний мінімум

Підходить для авто, де не потрібна деталізація по точках вивантаження
(наприклад ящикове завантаження, а не палетне).

```
Щоранку, один раз на день ("Старт зі складу"):
  ├── Одометр поточного ранку *
  └── Кількість палет * (загальна к-сть на весь день; можна лишити
      порожнім, якщо завантаження ящикове — коментар про це в "Нотатки")

  ✅ Тайл "Старт зі складу" блокується (сірий, з ✓) одразу після
     першого запису за день — повторно не натиснути (DriverDashboard.tsx)

Протягом дня, по одному разу на кожну накладну сьогоднішнього маршруту:
  └── "Скан накладної" (delivery, без одометра) — камера відкривається
      автоматично при вході на екран, форма з номером/датою з'являється
      лише після успішного скану; водій дописує Клієнта і Нотатку.
      ✅ Та сама накладна не може бути відскановано/збережено двічі за
      день — камера лишається відкритою з попередженням, доки не
      відскановано іншу

Опційно протягом дня:
  ├── Заправка (л + грн)
  ├── AdBlue (л + грн)
  ├── Інші витрати (грн + коментар)
  ├── Повернення — опційно (див. п. 4.3)
  └── Додатковий вантаж — опційно (див. п. 4.4)

Пробіг за день = одометр "Старт зі складу" сьогодні − одометр вчора
```

### Режим `full` — повний маршрут

Підходить для авто, де важлива деталізація по точках вивантаження.

```
Ранок (склад), один раз на день ("Старт зі складу", блокується так само
як у daily):
  └── Одометр *

Після кожного вивантаження ("Вивантаження" = delivery, full):
  ├── Одометр *
  ├── Кількість палет на точці *
  ├── Сканування QR накладної точки * — камера відкривається одразу,
  │   форма з'являється тільки після скану; повторний скан/збереження
  │   тієї ж накладної за сьогодні заблоковано (як і в daily)
  ├── Сканування інших накладних цієї точки (якщо є)
  ├── Відмова від поставки — опційно:
  │   ├── Повна відмова (відмітка на всю накладну)
  │   └── Часткова: артикул + кількість + коментар — ⏳ форма відмови
  │       (RejectionForm) ще не набрана, тип є в src/types/index.ts
  ├── Повернення — опційно (див. п. 4.3)
  └── Додатковий вантаж — опційно (див. п. 4.4)

У будь-який момент:
  ├── Заправка (л + грн)
  ├── AdBlue (л + грн)
  └── Інші витрати (грн + коментар)

Вечір (парковка):
  └── Одометр кінця маршруту *

Дає додатково:
  ├── Пробіг між точками вивантаження
  ├── Порожній пробіг (остання точка → склад наступного ранку)
  └── Час між вивантаженнями
```

✅ Всі 8 типів подій доступні через `EventForm.tsx`:
`depot_start`, `delivery`, `refuel`, `other_cost`, `return_goods`, `extra_cargo`,
`parking_end`, `depot_return` — набір полів на екран визначає
`getAvailableEventTypes(mode)` в `utils/eventHelpers.ts`; чи показувати
одометр — `requiresOdometer(type, mode)` (враховує режим саме через
розмежування вище).

✅ І "Історія" (`/driver/history`), і "Події сьогодні" на дашборді
показують праворуч компактні бейджі за наявними полями події (одометр,
№ накладної, літри, грн, кг — `eventSummaryBadges()`), а під назвою —
коментар водія (`notes`/`otherCostComment` — `eventComment()`), тож
"Повернення товару" зі сканом і коментарем видно в списку так само, як
одометр видно для "Старт зі складу".

### 4.3 Подія «Повернення»

Доступна в обох режимах. Водій вносить номер накладної клієнта вручну.
Матчинг виконує **менеджер-операціоніст** (⏳ UI матчингу ще не збудовано).

| Поле | Обов'язковість |
|------|---------------|
| Номер накладної клієнта | Обов'язково |
| Дата | Автоматично (поточна) |

### 4.4 Подія «Додатковий вантаж»

Доступна в обох режимах. Фіксує нетипові перевезення (не з основного реєстру).

| Поле | Обов'язковість |
|------|---------------|
| Номер накладної клієнта | Опційно (може бути `null`) |
| Звідки везуть товар | Обов'язково |
| Куди везуть товар | Обов'язково |
| Вага вантажу (кг) | Обов'язково |
| Коментар | Опційно |
| Дата | Автоматично (поточна) |

|------------|-----|---------|

### 5.5 Реєстр накладних (від менеджера, щотижня)

## 8. Аналітика

⏳ Жоден пункт цього розділу ще не має UI (`/analytics` — `PlaceholderPage`).
Формули розподілу вже частково реалізовані в `src/utils/calcTransportCost.ts`
(`allocateMonthlyCosts`, `allocateHiredTripCost`).

### По авто (власний автопарк)
- Пробіг за день / місяць (завантажений / порожній — тільки `full`)
- Витрати палива (л / 100 км), загальні витрати (грн / км)
- Кількість палет, вага та об'єм доставленого вантажу

### По накладній
- Транспортна собівартість (залежно від каналу доставки)
- % транспортних витрат від суми продажу
- Вага та об'єм вантажу

### По клієнту / магазину
- Транспортна собівартість, % від продажу
- Розбивка по каналах доставки
- Загальна вага та об'єм

### По товару / категорії
- Транспортна собівартість одиниці
- Вага / об'єм / об'ємна вага

### По каналу доставки
- Власний автопарк vs найманий транспорт vs служби доставки
- Порівняльна вартість грн/кг або грн/палета

### По маршруту (тільки `full`, власний автопарк)
- Пробіг між точками, час між точками, порожній пробіг

> ділить один застосунок (див. `CLAUDE.md`, розділ Obsidian vault sync).

| Компонент | Технологія | Примітка |
|-----------|-----------|----------|
| Framework | Django + DRF | Джерело правди по ендпоінтах — `DJANGO_CODING_GUIDE.md` у backend-репо |
| Auth | Django session + CSRF-cookie | `apiFetch` (`src/api/config.ts`) шле `credentials: 'include'` і `X-CSRFToken` — це не JWT bearer, а звичайна Django-сесія з CSRF-токеном |
| Реєстрація | Ручне підтвердження адміном | Новий акаунт створюється `is_active=False`; адмін підтверджує в Django Admin, отримує email-сповіщення |
| Containerization | Docker + Docker Compose | Деплой на Raspberry Pi через GitHub Actions + Cloudflare Tunnel (Фаза 4, `CODING_GUIDE.md`) |

### Мобільний доступ водія — Telegram Mini App, не звичайний PWA-інсталл

> Це найважливіша зміна відносно оригінального плану. Спочатку малось на
> увазі, що водій встановлює PWA на телефон напряму. У реалізації
> (Фаза 4.5 + пізніша сесія "редиректу Mini App за роллю") доступ іде
> через **Telegram-бота**: кнопка в боті відкриває `/driver-app`
> (`src/pages/DriverMiniApp.tsx`) всередині Telegram WebView, логін —
> через `window.Telegram.WebApp.initData` (без пароля), і вже звідти
> редирект за роллю (`driver` → `/driver`, `logist`/`manager`/`head` →
> `/fleet`). `vite-plugin-pwa`/manifest лишаються в конфігу, але
> production-шлях водія — саме через бота. Деталі налаштування бота —
> `TELEGRAM_BOT_SETUP.md` у `vehicle_tracker_api` (не в цьому репо).

### MVP (поточний scope)
- React SPA, частина екранів на mock JSON (`VITE_USE_MOCK`), частина вже
  на реальному Django API (auth, cars, drivers, route-events, waybills)
- Уся бізнес-логіка розрахунків — у `utils/`
- Мобільний доступ водія — Telegram Mini App (див. вище), а не інстальований PWA
