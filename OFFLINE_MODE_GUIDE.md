# Гайд: як додати офлайн-режим водію (для майбутньої розробки)

Статус на 2026-09-10: **офлайн-режиму НЕМАЄ**. Це не баг, а стан "ще не
робили" — документ фіксує, з чого стартувати, коли до цього дійдуть руки.
Не інлайн-нотатка в чаті, бо задача велика і краще матиме довге життя як
файл в репо (аналогічно `CODING_GUIDE.md`).

## Чому це взагалі спливло

Водій під'їздить на маршруті через зони без зв'язку (склади, підвали
магазинів, сільська місцевість). Кожна дія водія (`EventForm.tsx` →
`createEvent.mutateAsync(...)`) — це прямий `POST /route-events/` через
`apiFetch()` (`src/api/config.ts`). Без мережі `fetch()` кидає помилку,
`useCreateRouteEvent` (React Query mutation) переходить у `isError`,
форма показує `ErrorBanner` — і все, дані загублені, водій мусить
запам'ятати й ввести все вручну ще раз, коли з'явиться зв'язок.

## Поточний стан (перевірено 2026-09-10)

- **PWA precache — тільки app shell.** `vite.config.ts` → `VitePWA({
  workbox: {...} })` не має секції `runtimeCaching` взагалі. Workbox
  precache-ить лише збілджені статичні файли (JS/CSS/index.html/іконки),
  перелічені при `vite build` (зараз 6 записів, ~2.1 MiB — див. вивід
  `npm run build`). Жоден `/api/...` запит не кешується — GET-запити на
  дані (авто, водії, сьогоднішні події) йдуть у мережу щоразу, і без
  мережі падають з мережевою помилкою, а не віддають старі дані з кешу.
- **Нуль коду, пов'язаного з офлайном.** `grep -r "navigator.onLine\|
  serviceWorker\|indexedDB\|IndexedDB" src/` — 0 збігів у всьому `src/`.
  Немає індикатора "офлайн", немає черги неспроможних запитів, немає
  retry-логіки понад те, що дає React Query за замовчуванням (яке саме
  по собі НЕ зберігає між перезавантаженнями сторінки/закриттям вкладки).
- **`apiFetch()` (`src/api/config.ts:40`)** — це гола обгортка над
  `fetch()`: немає catch на мережеву помилку, немає fallback. Помилка
  просто прокидається вище, до `mutateAsync()` у формі.
- **`EventForm.tsx` (`src/pages/driver/EventForm.tsx:151`)** — головна
  точка, де офлайн боляче відчувається: `handleSubmit` робить
  `await createEvent.mutateAsync(data)`, і при груповому скануванні ще
  N додаткових `mutateAsync` у циклі (рядок 159-171) — кожен окремий
  network round-trip, кожен може впасти незалежно.
- **`registerType: 'autoUpdate'`** (vite-plugin-pwa) означає, що service
  worker вже присутній і активний на проді (підтверджено —
  [[vehicle-cost-tracker-deploy-pipeline]] в пам'яті: Telegram Mini App
  кешує старий бандл через нього). Це добра новина: інфраструктура SW
  вже є, лишається розширити її стратегію, а не ставити з нуля.

## Що саме зламається без мережі (по сторінках)

| Сторінка | Що відбувається офлайн |
|---|---|
| `DriverDashboard` (`useTodayEvents`, `useCar`, `useCurrentDriver`) | Якщо дані вже були завантажені в цю сесію — React Query покаже старі (stale) дані з in-memory кешу, поки компонент змонтований. Після перезавантаження вкладки — порожньо, крутиться `Spinner` вічно. |
| `EventForm.handleSubmit` | `mutateAsync` кидає помилку → `ErrorBanner`, дані форми (заповнені поля, відскановані накладні) залишаються в React-стейті компонента, але зникають при навігації/перезавантаженні. |
| `QRScanner` | Сам скан QR не потребує мережі (парсинг `parseQRCode` — локальний), ламається тільки збереження. |
| `DriverHistory`, `EventDetail` | Читання списку — та сама проблема, що й Dashboard. |

## План (рекомендований порядок, не обов'язково робити все і одразу)

### Крок 1 — індикатор "немає мережі" (найдешевше, найбільша користь відразу)
Простий `navigator.onLine` + `window.addEventListener('online'/'offline')`
хук (`useOnlineStatus.ts` в `src/hocks/`), банер у `DriverLayout.tsx`.
Не рятує дані, але хоча б водій ЗНАЄ, що зараз не збережеться, і не
натисне "Зберегти" наосліп. Дешево, без ризику, варто зробити першим.

### Крок 2 — офлайн-черга для запису подій (головна цінність)
Це основна робота. Ідея: `EventForm.handleSubmit` не викликає
`apiFetch` напряму, коли офлайн — кладе payload в чергу, яка живе довше
за один сеанс вкладки.

- **Сховище черги: IndexedDB**, не `localStorage` (localStorage
  синхронний і блокує потік на кожній операції; для черги, до якої
  постійно щось дописують/видаляють, це помітно гальмує на слабких
  телефонах водіїв). Або бібліотека `idb` (легка обгортка над
  IndexedDB), або власний мінімальний шар.
- Структура одного запису черги: сам payload `RouteEventCreate` +
  клієнтський `tempId` (`crypto.randomUUID()`) + `createdAt` +
  `status: "pending" | "syncing" | "failed"`.
- **Групове сканування (EventForm.tsx:159-171)** — кожен
  `mutateAsync` у цьому циклі стає окремим записом черги з тим самим
  `notes: withStopTag(mainEvent.id)`. Проблема: `mainEvent.id`
  сьогодні береться з ВІДПОВІДІ бекенду на перший запит — офлайн його
  ще нема. Треба або (а) прив'язувати групу локально через
  `tempId` головної події й переписувати `notes` при синхронізації
  партії, коли реальний `id` вже відомий, або (б) синхронізувати чергу
  строго послідовно (не паралельно) в порядку створення, щоб головна
  подія завжди йшла перед додатковими з тієї ж точки.
- **Синхронізація при відновленні зв'язку**: слухач `online` +
  опційно Background Sync API (`navigator.serviceWorker.ready
  .then(reg => reg.sync.register('sync-events'))`) — але Background
  Sync не підтримується в Safari/iOS, тож не можна покладатись ЛИШЕ на
  нього; тримати fallback на звичайний `online`-евент і/або
  періодичний retry, поки вкладка відкрита.
- **Показ водію**: бейдж "3 несинхронізовані" на Dashboard, окремий
  екран "Очікують синхронізації" зі списком і можливістю вручну
  повторити/видалити запис, що постійно падає (не просто мовчки
  ретраїти нескінченно).
- **Конфлікти**: дублікат-перевірка зараз (`isDuplicateForStage`,
  `EventForm.tsx:72`) звіряється з `todayEvents` — це запит з бекенду.
  Офлайн його або нема, або застарілий. Прийняти: дублікат-перевірка
  офлайн працює лише проти того, що вже є в ЛОКАЛЬНІЙ черзі за
  сьогодні; остаточна перевірка на дублікати — все одно бекенд
  (сервер має повертати зрозумілу 400-помилку на дублікат waybill,
  а не мовчки створювати другий запис — перевірити, чи це вже так).

### Крок 3 — кеш даних для читання (менш критично, робити після кроку 2)
`runtimeCaching` у `vite.config.ts`'s `VitePWA({ workbox: {...} })` для
`GET /api/cars/*`, `/api/drivers/me/`, `/api/route-events/?...` —
стратегія `NetworkFirst` (короткий timeout, наприклад 3с, потім фолбек
на кеш) для даних, які змінюються, `CacheFirst`/`StaleWhileRevalidate`
для майже статичних (список авто/водіїв). Приклад:
```ts
workbox: {
  runtimeCaching: [
    {
      urlPattern: ({ url }) => url.pathname.startsWith('/api/'),
      handler: 'NetworkFirst',
      options: { cacheName: 'api-cache', networkTimeoutSeconds: 3 },
    },
  ],
}
```
Обережно: `apiFetch` завжди шле `credentials: 'include'` і
`X-CSRFToken` — Workbox NetworkFirst сам по собі це не ламає (кешує
Response як є), але вартий перевірки: закешована відповідь під старим
CSRF-токеном не проблема для GET (CSRF перевіряється тільки на
мутаціях, які тут не кешуються).

### Крок 4 — офлайн-вхід (найскладніше, робити в останню чергу, можна пропустити)
Зараз логін і `useCurrentDriver()`/сесійні cookie теж вимагають мережі.
Якщо водій відкриває застосунок з нуля (закрита вкладка) повністю
офлайн — не увійде взагалі. Рішення (зберігати сесію локально й
довіряти їй, поки не підтвердиться інше) додає поверхню атаки
(протермінована/відкликана сесія, яку офлайн-клієнт не бачить) —
вимагає окремого рішення про прийнятний ризик, не технічна деталь.

## Що НЕ чіпати заради офлайну
- **Не** переписувати `apiFetch`/`fetchAllPages` (`src/api/config.ts`)
  під офлайн напряму — вони спільні для водія И офісних
  `/panel`-сторінок, яким офлайн не потрібен. Чергу й кеш-стратегію
  додавати окремим шаром НАД ними (у хуках `useCreateRouteEvent` тощо),
  не всередині.
- **Не** намагатися зробити офлайн універсальним для всього застосунку
  одразу — `/panel` (адмінка, імпорти, видалення) використовується в
  офісі з Wi-Fi, там немає сенсу ускладнювати. Це гайд конкретно під
  водійський флоу (`/driver/*`).
